# PMC-PaIR dataset construction pipeline

Code implementing **CHIPA** (Citation-guided Hierarchical Image-Pair Annotation), the workflow
behind **PMC-PaIR**, a dataset of positive medical image pairs and image-level labels derived
from published case reports in PubMed Central. Candidate case pairs come from
citation links in PMC-Patients; language models read the case descriptions, citation
evidence and figure captions (text only, no pixels) and propose image pairs that share
modality, anatomical region and pathology family.

One configuration file drives the whole workflow:

```
select-cases → download → extract-figures → filter-images → prepare-pairs
  → llm (annotation-ready pairs): citation-analysis → question-generation
       → answer-generation → pair-selection
  → finalize-pairs → label-images → split → export (+ checks)
```

[`docs/METHOD.md`](docs/METHOD.md) describes how each step is implemented and lists its
default parameters.

The deposited annotations were generated by earlier production workflows. This package is a
later implementation with changes to prompts and preprocessing. End-to-end regeneration of
the annotations has not been demonstrated; see [What can be reproduced](#what-can-be-reproduced)
for the steps that have been checked.

## Installation

Python ≥ 3.10 and the [Tesseract OCR](https://github.com/tesseract-ocr/tesseract) program
are needed.

In the repository folder:

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt                         # pinned dependency versions
pip install -e . --no-deps                              # editable: default paths point into the repository
# Tesseract: apt install tesseract-ocr | brew install tesseract | conda install -c conda-forge tesseract
```

Alternatively `conda env create -f environment.yml` (includes Tesseract), then
`conda activate pmc-pair` and `pip install -e . --no-deps`.

## Checking the downloaded Zenodo dataset

Once the dataset is available, download all files from its Zenodo record (see
[Data and weights](#data-and-weights)) into one directory. Before extracting the four ZIPs,
check their contents and the annotation files from the repository root:

```bash
python -m pmc_pair verify-deposit --data-dir /path/to/zenodo-download
```

This checks the deposited files directly. It needs no source articles, model responses,
API key or GPU. The split is distributed with the code rather than the dataset. To check
it too, add `--split-file image_splits.json`. The command leaves the downloaded files
unchanged; an optional `--report-file` must name a new file outside the download directory.

To repack a release from image and caption files, use `package-deposit` with explicit
input directories. See [`docs/DEPOSIT.md`](docs/DEPOSIT.md) for the downloaded file layout,
checks and repackaging command. These commands handle the Zenodo layout. The `export` and
`check` commands below handle the output of a pipeline run, which has a different layout.

## Quick start: synthetic example (offline, under a minute, no API key)

```bash
python examples/run_example.py      # builds examples/data/, runs every step, checks the release
python -m pytest                    # test suite; optional released-pairs check described below
```

The example uses invented articles (fake ids `PMC990000xx`), a local folder in the layout
of the PMC Cloud Service, the PMC-PaIR label taxonomy and ready-made model responses. It passes
through every filter: 11 candidate case pairs → 7 with a confirmed citation → 5
annotation-ready (model stages) → 5 image pairs.

## Running the full pipeline

Copy the configuration and set `paths.pmc_patients` ([locations](#inputs-and-outputs)). For a
run on your own data, also set `paths.existing_split: null`: the default names the benchmark
split, which fits only the released pairs.

```bash
cp config.example.yaml config.yaml          # then edit config.yaml as described above
python -m pmc_pair select-cases    --config config.yaml
python -m pmc_pair download        --config config.yaml   # resumable; reads the PMC Cloud Service
python -m pmc_pair extract-figures --config config.yaml
python -m pmc_pair filter-images   --config config.yaml   # resumable; CPU-heavy (scripts/slurm_job.sh)
python -m pmc_pair prepare-pairs   --config config.yaml
python -m pmc_pair status          --config config.yaml   # counts of the steps through split
```

**Language-model stages** (OpenAI Responses API; models and reasoning efforts in
`config.yaml`, prompts in [`prompts/`](prompts/)). They are paid, so nothing is sent unless
`--allow-api-calls` is given and `OPENAI_API_KEY` is set.

```bash
export OPENAI_API_KEY=...                                  # never write keys into files
python -m pmc_pair llm citation-analysis --config config.yaml          # dry run: writes request files, sends nothing
python -m pmc_pair llm citation-analysis --config config.yaml --limit 20 --sync --allow-api-calls   # small trial
python -m pmc_pair llm citation-analysis --config config.yaml --submit-batch --allow-api-calls     # Batch API
python -m pmc_pair llm citation-analysis --config config.yaml --collect-batch --allow-api-calls    # later; repeat until done
# then the same for question-generation, answer-generation and pair-selection
python -m pmc_pair run-all --config config.yaml --from finalize-pairs      # validation, labels, split, export
```

- **Alignment.** Each request has a stable id `<stage>:<case_pair_id>`, used as the Batch
  `custom_id`; responses are matched by id, never by line order.
- **Cache and resume.** Responses are stored in `<work_dir>/llm/<stage>/responses.jsonl` with a
  hash of the full request. A response is reused only for an identical request, so
  re-running is free and changing a prompt, model or input invalidates exactly the
  affected requests; `finalize-pairs` and `export` refuse outputs that no longer match.
  Downloads and image screening also resume after interruption.
- **Re-using outputs.** `--import-batch-output FILE --request-file FILE` imports a
  downloaded Batch output of this pipeline. `--import-responses FILE` attaches
  `{"request_id", "output_text"}` lines to the current requests *without* checking how they
  were produced (the example uses it); such responses are counted as "import" in
  `MANIFEST.json`.
- **Repeat runs can differ.** Model outputs are not deterministic and model snapshots
  change, so a repeat run can produce different annotations. Rebuilding a run exactly requires
  its archived response cache or Batch files and the matching pipeline version, dependencies,
  inputs and configuration.
- `run-all` runs every step from cached responses only and stops, with instructions, when
  responses are missing. It never calls the API. Exit codes: 0 done, 3 model responses
  still missing (`run-all` and `llm`), 1 error.

## Repairing pair-selection responses

`finalize-pairs` first uses the standard JSON parser. If parsing fails, the code extracts
one array from surrounding text and attempts local syntax repair with the pinned
`json-repair==0.64.0` dependency in strict mode. Valid JSON of the wrong structure, competing
arrays and ambiguous malformed input are rejected. Repair does not call an API or supply
missing clinical content. Repaired responses pass the same proposal checks as responses
parsed directly. Raw cached responses stay unchanged, and every attempt is recorded in
`<work_dir>/image_pairs/response_repairs.jsonl`. See [`docs/METHOD.md`](docs/METHOD.md) and
[`docs/OUTPUTS.md`](docs/OUTPUTS.md) for the rules and the recorded evidence.

## Inputs and outputs

Inputs: a PMC-Patients table regenerated with the PMC-Patients code (locations at the end of
this section), the PMC Open Access articles (downloaded), the label taxonomy
(`label_taxonomy.json` in this repository, also released with the dataset) and the benchmark
split (`image_splits.json` in this code repository, see Benchmark split). A pipeline run writes
per-step files to `paths.work_dir` and a release to `paths.release_dir` (defaults `data/work`
and `data/release`; file names in `release.file_names`):

| Release file | Content |
|---|---|
| `image_pairs.json` | image pairs with shared modality, anatomy, diagnosis and both captions |
| `image_labels.jsonl` | modality / anatomy / diagnosis labels per image |
| `label_taxonomy.json` | vocabulary and mapping rules (the file of this repository) |
| `case_pair_citations.json` | citation passages and citation analyses of the annotation-ready case pairs |
| `image_splits.json` | train / val / test per image (article-disjoint; see Benchmark split) |
| `images_part_NNN.zip` | the image files |
| `MANIFEST.json`, `CHECKS.json` | checksums, settings and statistics; check results |

Formats: [`docs/OUTPUTS.md`](docs/OUTPUTS.md). Label taxonomy and mapping: [`docs/LABEL_RULES.md`](docs/LABEL_RULES.md).
The Zenodo deposit uses `case_pair_citations_eligible.json`, four `images_captions_NNN.zip`
archives and licensing metadata, and does not contain a split file. Its pair records have no
`captions` field, because the captions are in the ZIPs. Its layout is described in
[`docs/DEPOSIT.md`](docs/DEPOSIT.md).

Not included: the regeneration of PMC-Patients (use the PMC-Patients code), the license
review, withholding decisions and creation of the deposit's metadata files, and the
experiments of the Data Descriptor's Technical Validation.

## Benchmark split

`image_splits.json` in this repository is the PMC-PaIR benchmark split (SHA-256
`b0b7be4be1597fa4e557fa4c5a51d0148361c2f253a604cf3df4a95a277c30eb`, also listed in
[`SHA256SUMS`](SHA256SUMS)). It is distributed with the code, not in the Zenodo data
files. The `pmc-pair-retrieval` repository includes the same assignments as
`data/article_disjoint_split.json`. The split is article-disjoint:

1. Images are nodes and positive image pairs are edges; the connected components are formed.
2. Components that share a source article (the PMC number at the start of the image ID) are
   merged into groups.
3. The groups are sorted by their smallest image ID, compared as strings, and shuffled with
   `random.Random(42)`.
4. Whole groups are assigned by group count: the first `int(0.8 * N)` groups to train, the next
   `int(0.1 * N)` to val and the rest to test, for N groups (both products rounded down).

| Partition | Images | Image pairs | Article groups |
|---|---:|---:|---:|
| train | 70,552 | 70,262 | 10,670 |
| val | 8,245 | 8,034 | 1,333 |
| test | 8,096 | 7,848 | 1,335 |
| total | 86,893 | 86,144 | 13,338 |

Every image has exactly one partition, and no source article and no image pair spans two
partitions. To regenerate the split from the released pairs and compare it, image by image,
with the packaged file (standard library only; exit status 1 on any difference):

```bash
python scripts/generate_splits.py --pairs /path/to/zenodo-download/image_pairs.json
```

The script also rejects repeated pairs, self-pairs and malformed image IDs, and checks the
packaged file against `SHA256SUMS`. `--output FILE` writes the regenerated split (only if
every check passes) and `--report FILE` the computed counts; existing files are never
overwritten.

The `split` step uses the same file (`paths.existing_split`). It checks the file's SHA-256
(`split.expected_sha256`), its coverage and integrity, and that it equals the split
regenerated from the pairs of the run. The release checks repeat the coverage, integrity and
regeneration checks on the released pairs. For another set of pairs, set
`paths.existing_split: null`; the step then draws the split with the same procedure and seed
(a non-negative integer). Turning off `split.verify_regeneration` is recorded as a warning in
`<work_dir>/split/stats.json` and `CHECKS.json`, as is an empty partition.

## Checks

For files downloaded from Zenodo, use `verify-deposit` as described above and in
[`docs/DEPOSIT.md`](docs/DEPOSIT.md). The following checks apply to the output of a pipeline
run.

`export` writes the release to `<release_dir>.incomplete` and moves it into place only if
all checks pass; `python -m pmc_pair check --config config.yaml` repeats them. They cover
misaligned records (captions vs. `pair_id`, citation record for every pair), invalid or
duplicate pairs, labels outside the vocabulary or different from labels recomputed from pairs,
captions and taxonomy, splits that miss images, separate the images of a pair or of a source article, or
differ from the split regenerated from the released pairs, missing image files, and files that
differ from the SHA-256 recorded in `MANIFEST.json`.

The tests cover the example run, the scope of each model stage, batch handling with a fake
client, cache and stale-output rules, the repair of malformed responses, the label examples
in `tests/label_examples.json`, the article-disjoint split, the deposit checks and
repackaging, and that the checks detect deliberately corrupted releases. An optional test
regenerates the benchmark split from the released pairs; it runs only when
`PMC_PAIR_RELEASE_PAIRS` is set to a release's `image_pairs.json`.

## What can be reproduced

These checks run on a CPU and need no API key. The first three start from the deposited
files; the results below come from a copy of those files.

| Kind | What is run | Result | Where |
|---|---|---|---|
| Regenerating the labels | the label comparison of [`docs/LABEL_RULES.md`](docs/LABEL_RULES.md#comparing-with-existing-labels) on the deposited `image_pairs.json`, `label_taxonomy.json` and `image_labels.jsonl` and the extracted captions | no difference in any field for the 86,893 records (the 68 withheld images have no caption file; the caption rule changes none of them) | label rules: [`docs/LABEL_RULES.md`](docs/LABEL_RULES.md) |
| Regenerating the split | `scripts/generate_splits.py` on the deposited `image_pairs.json` | byte-identical to `image_splits.json` | Benchmark split, above |
| Checking the deposit | `verify-deposit` | checksums, archive contents and records agree | [`docs/DEPOSIT.md`](docs/DEPOSIT.md) |
| Running the workflow | `examples/run_example.py` and the tests | every step runs on invented articles with ready-made responses | Quick start, above |
| Regenerating the pair annotations | not tested with live model calls | end-to-end annotation regeneration has not been demonstrated; the label and split checks start from the deposited pairs | Not demonstrated |
